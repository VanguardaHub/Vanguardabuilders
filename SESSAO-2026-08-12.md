## 1. Correção do erro em produção (cliente + SSR)

Sintoma: "Algo deu errado" em todas as páginas, mesmo com o SSR servindo o HTML
correto.

Causa raiz: o `VITE_SUPABASE_URL` foi embutido no build com um valor **inválido
porém não-vazio** (vindo do painel do Vercel). O fallback antigo (`env || fixo`)
só agia quando a env estava *vazia*, então o valor inválido passava direto e
quebrava o `createClient` com `Invalid supabaseUrl`.

Correção: validar a URL (regex `http(s)://`) e cair no fallback público quando a
env estiver **ausente ou inválida**. Aplicado em `client.ts`, `auth-middleware.ts`
e `client.server.ts`. Provado localmente (build com env inválida → bundle sai
com a URL correta embutida).

- `2bf4c0e` fix(supabase): validar URL e usar fallback em valor inválido, não só vazio

> Também consolidou correções da virada do dia anterior já commitadas hoje:
> acesso *lazy* ao client Supabase para não quebrar o SSR no carregamento do
> módulo (`50c6b16`), fallback público de URL+publishable no client (`c8a5c08`)
> e runtime do Vercel fixado em Node 22 (`1e74c07`).

## 2. Migração de dados do Lovable (origem → destino)

O projeto de origem é gerenciado pelo Lovable — **sem credencial de banco
direta**. A ponte foi feita por MCP: leitura via MCP do Lovable
(`query_database`) e escrita via MCP do Supabase (`apply_migration`).

**Tabelas e auth** (payloads grandes trafegaram em base64 para evitar problemas
de escape):

| Entidade | Qtde | Observação |
|---|---|---|
| `auth.users` | 2 | IDs preservados (Joyce, Bruna) |
| `auth.identities` | 3 | Google + e-mail — login segue válido |
| `profiles` | 2 | ajustados para bater com a origem |
| `clients` | 3 | — |
| `landing_pages` | 2 | com HTML (13,5 KB) e assets |

**Storage** (`project-materials`, 4 arquivos): o bucket de origem foi tornado
público temporariamente, os arquivos baixados via `curl`, o bucket restaurado
para privado, e os arquivos reenviados ao destino com a **service_role** (que
ignora o RLS), preservando os caminhos exatos. Tamanhos validados no destino
(10.350 / 23.162 / 6.051.112 / 23.162 bytes).

Nenhuma alteração de código — feito inteiramente via MCP.

## 3. Remoção da última amarra de IA (Lovable AI Gateway)

A geração de landing pages ainda usava o `LOVABLE_API_KEY` via
`ai.gateway.lovable.dev`. Trajeto do dia:

1. **OpenRouter** (`479cd55`) — drop-in OpenAI-compatível; removidos arquivos
   órfãos (`ai-gateway.server.ts`, `integrations/lovable/index.ts`) e 3 deps sem
   uso (`@ai-sdk/openai-compatible`, `ai`, `@lovable.dev/cloud-auth-js`).
2. **Troca para Google Gemini** (`6e59bd6`) — OpenRouter é pago; o AI Studio tem
   tier gratuito. Endpoint OpenAI-compat do Google, modelos
   `gemini-flash-latest` / `gemini-pro-latest`, GPT removido do seletor.
3. **API nativa do Gemini** (`f0c8539`) — o endpoint OpenAI-compat do Google
   recusa PDFs (`Invalid content part type: file`). Trocado para
   `generateContent`, que lê imagens **e** PDFs inline via `inlineData` (base64),
   restaurando a leitura multimodal. Prompts e schema de saída inalterados.

Resultado: geração testada em produção com PDF + imagem → **sucesso**.
`@lovable.dev/mcp-js` foi mantido (é o servidor MCP que o próprio app expõe).
